# Грабли и выводы

Каждый пункт стоил времени на реальной сборке. Следующему агенту искать заново
не нужно.

## Скриншот слайда это тупик для задачи

Два первых скрипта снимали слайд в PNG и вставляли картинкой. Выглядит точно,
но редактировать нечего. Чинить их бесполезно, подход не отвечает цели. Путь к
редактируемости один: пересобирать каждый элемент нативным объектом по
измеренной геометрии.

## file:// заблокирован в MCP-браузере

Встроенный браузер Playwright через MCP не открывает `file://`
("Access to file: protocol is blocked"). Решение: поднять локальный HTTP-сервер
и грузить по `http://127.0.0.1:8777/`. В Python-версии Playwright `file://`
работает, поэтому в самостоятельном пакете сервер не обязателен. Текущий
`build_pptx.py` жестко ждет URL на 8777, это стоит убрать (см.
[05-next-steps.md](05-next-steps.md)).

## Прямоугольник текста снимать через Range, а не через элемент

`element.getBoundingClientRect()` дает border-box, с учетом padding и лишнего
места. Для позиции текста это мимо. `Range.selectNodeContents(el)` с
`getBoundingClientRect()` дает точный ink-бокс: где реально стоят буквы, с
учетом выравнивания и переносов. Это единственный способ попасть в позицию,
которую задает центрирование внутри карточки.

## Перенос строк ломает короткие подписи

Первая сборка переносила "Преподаватель" как "Преподавател" плюс "ь" на новой
строке, "ИНФОРМАЦИОННАЯ" аналогично. Причина: Arial в PowerPoint чуть шире, чем
в Chromium, а бокс равнялся точной ширине текста. Последняя буква не влезала и
уезжала вниз.

Решение: перенос включать только для реально многострочного текста, условие
`h > size*1.6` и отсутствие явного `\n`. Короткие метки ставятся без переноса,
при нехватке ширины текст выходит за рамку, но не ломается. Плюс небольшой запас
по ширине (8px). Это компромисс: если в такую метку впечатать заметно более
длинный текст, он вылезет за рамку.

## Односторонняя граница не ложится в рамку фигуры

У прямоугольника PPTX рамка только по всему периметру. Левые полосы `.mini` и
`.explain`, верхние полосы карточек выводов рисуются отдельной тонкой залитой
фигурой поверх фона. Определение в `extract.js`: четыре стороны сравниваются по
ширине и цвету, при неравенстве пишется заливка плюс полосы по сторонам.

## Текст диаграмм: картинка без текста плюс нативный текст поверх

Диаграммы (inline SVG на слайдах 3, 6, 7; viewBox 900x290, 500x285, 900x290)
содержат и графику, и подписи. Графику родными фигурами не собрать надежно
(пути, стрелки). Решение: скриншот SVG с погашенным через CSS текстом
(`svg:not(.lucide) text{visibility:hidden}`) дает картинку без подписей, а сами
подписи извлекаются как нативный текст и кладутся поверх. Диаграмма выглядит
один в один, подписи редактируются.

Тот же прием у кота: подпись "информация найдена" гасится перед скриншотом
карточки и кладется нативным текстом сверху.

## px в pt это 0.75, px в EMU это epx

Две разные единицы. Кегль шрифта в пунктах: `px * 0.75` (72/96). Координаты и
размеры фигур в EMU: `px * epx`, где `epx = 12192000/1160 = 10510.34`. Перепутать
легко, глядя на результат: неверный масштаб текста при верных фигурах значит,
что кегль умножен не на то.

## Растр в двойном разрешении

`device_scale_factor=2` при съеме иконок. Иконка 22px скриншотится как 44px,
вставляется размером 22px, край чистый. При `factor=1` мелкие иконки мылят.

## Проверять результат рендером PowerPoint

Типы и счетчики объектов не видят экран. Проверка велась экспортом PPTX в PNG
через COM PowerPoint (`Presentations.Open`, `SaveAs(dir, 18)`, где 18 это
`ppSaveAsPNG`), затем сверкой картинок с исходным HTML. Именно так нашлись
переносы строк. LibreOffice дал бы то же самое (`soffice --convert-to`), но в
системе его нет.
