# Архитектура

## Проблема

Готового инструмента, который превращает произвольный HTML+CSS+SVG в
пиксель-в-пиксель редактируемый PowerPoint, нет. Два предыдущих скрипта
(`html_to_pptx.py`, `html_to_pptx_v7_config (1).py`) снимали каждый слайд в PNG
и клали картинкой на весь слайд. Внешний вид сохранялся точно, редактировать
было нечего. Цель проекта требует обратного: текст и фигуры как родные объекты.

Полная точность и полная редактируемость частично противоречат друг другу.
Иконки, сложные схемы и декоративная графика в родные фигуры переводятся плохо.
Отсюда выбор из трех вариантов.

## Три варианта

Вариант A, браузерный. Агент пишет HTML+CSS свободно, конвертер рендерит его
настоящим Chromium и снимает геометрию каждого элемента. Дает почти любой
дизайн и произвольные схемы. Требует Playwright и бинарь браузера. Строгость
держится на дисциплине агента, а не на движке: редкие CSS-приемы дают тихие
артефакты.

Вариант B, строгий DSL без браузера. Ограниченный набор компонентов, раскладку
конвертер считает сам. Установка через `pip` без бинарей, результат
предсказуем и тестируем. Произвольную верстку и нестандартные схемы сделать
нельзя.

Вариант C, гибрид. Выбран.

## Выбор: гибрид

Строгий набор компонентов образует основной путь: заголовок, подзаголовок,
абзац, список, сетка карточек, готовые блоки-узлы схемы, картинка. Эти
компоненты дают нативные объекты и покрываются golden-тестами. Для нестандартной
графики есть люк: атрибут `data-raster` на произвольном SVG или блоке. Такой
элемент растрируется картинкой, а его текст остается редактируемым, наложенный
поверх. Так сделаны диаграммы и кот в прототипе (см. [02-converter.md](02-converter.md)).

Строго там, где движок гарантирует результат. Свобода там, где нужна своя
схема, ценой того, что графика люка нередактируема.

Playwright в гибриде нужен: и для растра `data-raster`, и для съема точной
геометрии основного пути. Отказ от браузера остается возможным для тех
компонентов, чью раскладку движок умеет считать сам, но это отдельная работа
(см. [05-next-steps.md](05-next-steps.md)).

## Структура будущего репозитория

Предложение, не реализовано.

```
├─ AGENTS.md            контракт HTML для агента: компоненты, что во что мапится
├─ spec/schema.md       формальная грамматика, таблица компонент -> объект PPTX
├─ src/<pkg>/
│   ├─ validate.py      проверка HTML против контракта, понятные ошибки
│   ├─ extract.js       съем геометрии (есть прототип)
│   └─ build.py         сборка PPTX из фигур и текста (есть прототип)
├─ examples/            эталонные HTML и собранные из них pptx
├─ tests/               golden: HTML -> PPTX -> PNG, сверка с эталоном
├─ pyproject.toml       CLI-точка, напр. deck build slides.html -o out.pptx
├─ README.md, LICENSE, CI
```

Контракт `AGENTS.md` это сердце проекта. Агент читает его и генерирует HTML
строго по нему, а `validate.py` не пропускает то, что движок не гарантирует.
Набросок контракта: [04-html-contract.md](04-html-contract.md).
